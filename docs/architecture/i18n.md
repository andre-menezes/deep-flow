# Internacionalização (i18n)

## Objetivo

Definir como textos de UI e erros de API são organizados no frontend Studia (Vue I18n).

## Escopo

- Idiomas MVP: **pt-BR** e **en**
- Mensagens por feature + mensagens compartilhadas mínimas
- Mapeamento `error.code` → chave i18n

## Fora do escopo

- Tradução automática / CMS de copy
- RTL
- Pluralização avançada além do que Vue I18n oferece nativamente
- Design de tom de voz detalhado (produto: assistir/organizar, não punir)

## Regras

1. Toda string visível ao usuário deve passar por i18n (templates e toasts).
2. Idiomas iniciais: `pt-BR` e `en` — **sempre** adicionar a chave nos dois ao criar copy.
3. Organização:
   - `src/features/<name>/locales/{pt-BR,en}.json` — copy da feature
   - `src/shared/i18n/locales/{pt-BR,en}.json` — apenas transversal (ex.: `errors.*`, `common.*`) com **≥2** consumidores reais
4. Locale default: `pt-BR`. Detecção inicial pode usar `navigator.language`; o usuário pode trocar manualmente (persistência em FEATURE futura de settings se necessário).
5. Erros de API: usar `errors.<CODE>` conforme `docs/api/error-codes.md` (ADR-0005 / ADR-0007). Fallback: `errors.INTERNAL_ERROR`.
6. Nunca exibir `detail`/`title`/`message` crus do backend.
7. Interpolação: preferir named (`{name}`) em vez de concatenar strings traduzíveis.

## Anti-exemplos

```vue
<!-- ERRADO -->
<button>Criar Study</button>
```

```ts
toast.error(error.detail)
if (plan === 'FREE') { /* copy hard-coded */ }
```

## Exemplos

```vue
<button>{{ t('studies.wizard.submit') }}</button>
```

```ts
t(`errors.${code}`, t('errors.INTERNAL_ERROR'))
```

## Resultado esperado

UI bilíngue previsível; Mock/API e client compartilham o mesmo vocabulário de `code`.
